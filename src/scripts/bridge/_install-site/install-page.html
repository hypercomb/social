Run your own
corner of the internet.

Everything you need to install Hypercomb and host it yourself — the same setup that serves this very page. Five steps, no getting stuck: every trap we hit is written down below so you don't have to hit it too.

The shape of what you're building

One machine, one tunnel, one worker. Nothing rented but the domain.

The gold path is public content: a Cloudflare worker answering every subdomain of your domain from a bucket of signed, immutable files. The grey path is you: your own domain riding a tunnel straight to the app on your machine. Publishing a hive branch named garden makes garden.yourdomain.com its website — no per-site setup, ever.

The five steps

Steps 1–2 get you running. Steps 3–5 put you on your own domain.

1

Install the app

One link, always the latest build. Run it — the app is the whole host: your hive, your relay, your publisher. Nothing else to install.

Download for Windows

The link 302s to the newest signed build. Your data lives on your machine from the first minute — there is no account to create.

2

Get a domain onto Cloudflare

A free Cloudflare account and any domain. Add the domain as a zone, then create one wildcard record so every future site name already resolves:

# DNS → Records → Add record
Type CNAME   Name *   Target yourdomain.com   Proxy ON (orange cloud)

The wildcard certificate covers one label deep: garden.yourdomain.com is covered, a.b.yourdomain.com is not.

3

Point the tunnel at your machine

The app can connect Cloudflare for you (Host → Connect Cloudflare — it logs in, creates the tunnel, and sets the DNS route). The manual recipe, if you'd rather see it:

# ~/.cloudflared/config.yml
tunnel: <your-tunnel-id>
ingress:
  - hostname: yourdomain.com
    service: http://localhost:7777
  - service: http_status:404

Run cloudflared tunnel run as a service so it survives reboots. Traffic to your domain now lands on the app — no open ports, no fixed IP.

4

Deploy the content worker

This is the public face — it serves your published sites even when your machine is off. From the blossom-worker folder, once:

wrangler r2 bucket create hypercomb-content
wrangler kv namespace create GRANTS     # paste the id into wrangler.toml
wrangler kv namespace create HIVES      # paste the id into wrangler.toml
# edit the two route lines to your domain, then
wrangler deploy

The worker's wildcard route makes every subdomain a site address from day one. content.yourdomain.com becomes the write face your app publishes to — it is never a site itself.

5

Publish

In the hive: mark a branch public, open Publish, press it. The name is the address — a branch called garden goes live at garden.yourdomain.com the moment your signed index carries it.

Publish seals the branch, pushes the signed bytes, waits until the host actually serves them back, and only then moves the pointer. "Confirmed" means the world can see it — not that a server accepted an upload.

Without getting stuck

Every one of these cost us real time once. They don't have to cost you any.

  • Check headers before blaming routing. A 404 from your content host that carries X-Reason: sig not held is the worker answering honestly — the object is missing, the routing is fine. curl -sI first; we lost an hour to this one.
  • Node 24 + npx don't mix here. npx wrangler can die with EINVAL on Windows. Call it directly: node node_modules/wrangler/bin/wrangler.js …
  • Git Bash eats leading-slash arguments. It rewrites /branch into a Windows path before your script ever sees it. Pass the bare name, or use PowerShell.
  • One tab. Your hive has exactly one writer. Opening it in a second tab gives the second tab a dead store — close it, don't fight it.
  • "Unconfirmed" is patience, not failure. The edge sometimes takes a moment to serve a fresh publish back. The row re-checks itself — don't republish in a loop.
  • The wildcard covers one label. Nested names like a.b.yourdomain.com need their own explicit setup; flat names never do.
