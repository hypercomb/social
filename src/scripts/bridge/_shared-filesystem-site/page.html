Hypercomb · content-addressed publishing

Publish by Signature

Every hosted subdomain is a window onto one shared, signature-addressed file system. A file's name is the SHA-256 of its bytes — so publishing any project means uploading only the signatures the store doesn't already hold, and duplication is structurally impossible.

Six hostnames, one store

One worker script answers for every hostname. Each site is nothing but a lineage head — a pointer at a root cell inside the same store. Where two sites use the same content, they reference the same cell.

Figure 2 — an incremental publish

A publish is a set difference

You edit one file in one project. Signing the build shows exactly what changed: the edited layer gets a new signature, the root recomposes above it, and everything else keeps the signature it always had. The store is asked one question per cell — do you already hold this sig?

Why this is fast — and can't be redundant

Deduplication is structural

The file's name is the hash of its bytes. If two projects — or two hundred — use the same picture, layer, or note, they hold the same signature and reference the same single cell. There is no copy to make, so there is no copy to drift, and no cleanup pass to run.

Publishing is a set difference

The publisher never asks "what changed?" — it asks the store "which of these signatures do you lack?" Unchanged files keep their signatures forever, so most publishes are a handful of cells and a marker flip, no matter how large the project has grown.

Immutable means cacheable forever

A sig-named cell can never change — new content is a new signature. Edges and browsers can cache every cell indefinitely with zero risk of staleness; going live is just one tiny head marker pointing at a new root.
