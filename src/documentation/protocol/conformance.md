# The Hypercomb protocol — conformance specification

This is the contract between independent implementations of Hypercomb. It exists
because the TypeScript shell is no longer the only participant: `Hypercomb.Net`
(C#) reads and writes the same content-addressed tree and joins the same mesh.

**The protocol is the interop surface, and it is the ONLY interop surface.**
Two implementations meet at exactly three places:

1. **Signatures** — identical bytes in, identical hex out.
2. **Storage layout** — flat sig-named entries, sig-named lineage bags, pools of meaning.
3. **Mesh events** — nostr event shapes and the payloads inside them.

Everything else — EffectBus, IoC keys, Angular signals, Pixi rendering, OPFS
handles — is *shell-local by design* and deliberately NOT shared. If a
`Hypercomb.Net` type ever needs to know about `window.ioc`, the boundary has
leaked and the design is wrong.

Machine-checkable vectors for every rule below live in
`hypercomb-client/conformance/vectors.json`, generated by
`hypercomb-client/conformance/generate-vectors.ts` **by executing the live
TypeScript implementation**. They are never hand-written. Regenerating them is a
protocol change and must be reviewed as one.

```bash
npx tsx hypercomb-client/conformance/generate-vectors.ts
```

## 1. Signatures

A signature is the **SHA-256 of the content bytes, rendered lowercase hex,
always 64 characters**. There is no salt, no prefix, no length framing, no
domain separation.

```
signature(bytes) = hex(sha256(bytes))
```

Source of truth: `hypercomb-core/src/core/signature.service.ts`.

Text is hashed as **UTF-8**. Conforming implementations must match on non-ASCII
input — the vectors pin CJK, astral-plane (surrogate pair) and combining-mark
cases specifically.

**Unicode normalization is NOT applied at the signing layer.** `sign()` hashes
exactly the bytes it is handed. Normalization happens *upstream*, in lineage-key
canonicalization (§2) and nowhere else. A composed and a decomposed `café` are
therefore **different signatures** but the **same lineage bag** — the vectors
assert both halves of that, because getting it backwards silently forks either
content identity or a user's history.

### The root signs as empty

`sign("")` = `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`
— the SHA-256 of zero bytes. This is also the **root lineage bag address**,
because the root's lineage key is the empty string.

This collision is real, load-bearing, and has caused bugs before. Any code that
walks the root must not assume the empty hash is "nothing".

## 2. Lineage keys — the address of a place

A lineage sigbag's identity IS its ancestry. The bag address is
`sha256(lineageKey(segments))`.

Source of truth:
`hypercomb-essentials/src/history/lineage-key.ts`.

### Canonicalization rule

Per segment:

1. Normalize to **NFC**.
2. Replace every **run** of characters that is neither a Unicode letter (`\p{L}`)
   nor a Unicode number (`\p{N}`) with a **single** `-`.
3. Strip leading and trailing `-`.

Then: drop segments that were empty to begin with, and join the rest with `/`.

**Case is preserved.** Letters and digits of *any* script survive — `日本語` and
`café` keep their identity. Stripping to ASCII would collapse every non-Latin
name into the same bag.

Collapsing separator runs to a hyphen (rather than deleting them) preserves word
boundaries, so `AB-CD` cannot collide with a real `ABCD`.

The rule is **idempotent** — canonicalizing an already-canonical segment is a
no-op, so it is safe to apply at any join site.

### The symbol-only guard

A non-empty segment that canonicalizes to `""` (emoji, pure punctuation) falls
back to its **trimmed raw form** instead of being dropped. Dropping it would
shorten the path and collide with the parent — or, for a single segment at the
root, collapse the key to `""` and collide with the **empty-content root sig**.

This guard is not optional. An implementation that omits it will, the first time
a user names a tile `🐝`, write that tile's history into the root's bag.

### Scope

Canonicalization is **sig-side only**. The URL, the explorer path, and on-disk
folder names stay lossless — `My-Tile` still *displays* as `My-Tile`. Only the
preimage that gets hashed is folded.

### The legacy raw key

`rawLineageKey` (trim + drop-empty + join, **no** punctuation folding) is what
was hashed before canonicalization existed. It is a **read-only migration
source**: when canonicalization changes a lineage's key, the bag stored under the
old address is unioned into the new one. It is **never a write destination**.

A conforming implementation must read the legacy address, must union it, and
must never write to it.

## 3. Pools of meaning vs lineage bags

The storage root is an **untagged union** of two kinds of sig-named directory:

```
pool address = sha256(meaning)
bag address  = sha256(lineageKey(segments))
```

Nothing on disk distinguishes them. For a **bare-word** meaning the two preimages
are byte-identical and the addresses **are the same directory**.

The vectors enumerate this census. As generated, **21 of 27 registered pool
meanings collide** with a same-named root tile:

> `authored`, `bees`, `clipboard`, `computation`, `dependencies`, `host-push`,
> `host-receipts`, `manifests`, `optimization`, `overrides`, `patches`, `push`,
> `receipts`, `registry`, `roots`, `structure`, `temporary`, `threads`,
> `translations`, `viewport`, `visual-optimization`

The 6 colon-scoped meanings (`pheromones:deposits`, `substrate:references`,
`substrate:sources`, `tutorial:artifacts`, `usage:dwell`, `websites:menu`) do
not, and cannot.

### The colon rule

`lineageKey` folds every non-letter/number to `-`, so a **`:` can never appear in
a lineage key**. Therefore a colon-carrying meaning is collision-proof *by
construction*.

**Every NEW pool meaning MUST carry a colon.** The bare-word set is frozen and
may only shrink. Renaming a meaning is not a code change but a **data
migration** — `sign()` of a new spelling mints a different address forever and
strands every existing member.

### Never keep a local list

Any implementation that walks, prunes, or enumerates the root **must consult the
registry** before treating a sig-named directory as a lineage bag. A fixed list
goes stale the moment any module mints a pool, and modules are the whole point of
the architecture. Four separate copies of such a list had already drifted in the
TypeScript tree, and `/flatten` on a colliding bare-word address hard-deleted an
entire pool.

The registry is both **seeded** with the full census and **self-extending** —
deriving a pool address registers it.

Source of truth: `hypercomb-core/src/core/pool-registry.ts`.

## 4. Layers

A layer is the unit of mutation. Its signature is the SHA-256 of its **canonical
JSON bytes**.

Source of truth:
`hypercomb-essentials/src/history/canonical-layer.ts`.

### Canonical form

- `name` is always present and always **first**. It is the layer's only intrinsic.
- Every other field is a **slot** — an open set contributed by registered
  subsystems. Slots follow `name` in **alphabetical order by key**, so byte output
  is stable regardless of registration or mutation order.
- `children` is **just another slot**. It gets no special positioning. An
  implementation that hardcodes it will produce wrong bytes the moment a slot
  sorting before `c` appears.
- Slot values pass through **untouched** — each slot owns its own internal
  canonical form.
- **Dropped entirely**: `undefined`, `null`, empty arrays, empty objects. This is
  the *sparse-layer invariant* — absent fields cost nothing and an empty field
  must not change the signature.

Byte form is `JSON.stringify` of the result: **no whitespace**, `,` and `:`
separators with no spaces, standard JSON string escaping.

The empty layer minted on a bag's first touch is therefore `{"name":""}` — with
**no** `children` key at all.

> ⚠️ **Trap.** `history.service.ts` exports
> `EMPTY_LAYER_CONTENT_SIG = a8a9aaac…`, documented as the hash of
> `{"children":[],"name":""}`. That constant is **inconsistent with the
> canonicalizer**, which drops empty arrays and puts `name` first, and so emits
> `{"name":""}` → `1390696a…`. The constant currently has no live consumers. Do
> not port it. See §8.

### Child order is content

`children` is **not sorted**. It is the user-visible order of tiles and is
semantically meaningful. Sorting it would change the signature and scramble the
user's layout.

### The cascade

Parents reference each child's *current* layer sig in their `children` array.
Committing walks leaf → root, minting a new layer and marker at each level. The
root lineage's latest layer sig **is** the global merkle root.

## 5. Lineage bags and markers

A bag is a sig-named directory holding zero-padded 8-digit marker files:

```
<root>/<lineageSig>/00000000
<root>/<lineageSig>/00000001
<root>/<lineageSig>/00000002
```

**The lexicographically maximum marker filename IS the head.** Filenames carry no
other meaning. There is no separate head pointer to keep in sync — and therefore
none to corrupt.

### Marker records

A modern marker is a **pointer record** naming which layer this revision points
at:

```json
{"layer":"<64-hex sig>"}
```

The marker is *meta*; the layer itself is root content. A marker may carry
additional named sig fields (decorations, context, receipts) — versioning, undo
and shareability come free because **the marker IS the revision**.

### Legacy inline markers

Older markers contain the **full layer JSON directly** — the bytes themselves
were the layer.

Detection rule: parse the bytes; if the result has a `.layer` field matching
`^[0-9a-f]{64}$` it is a pointer record. Otherwise the bytes **are** the layer and
its sig is `sha256(marker bytes)`.

An implementation must read both shapes. It should migrate opportunistically on
read. It must only ever *write* pointer records.

## 6. Bee payloads — a DIFFERENT canonical rule

`PayloadCanonical` hashes `JSON.stringify(payload)` in **insertion order**. Keys
are **NOT sorted**.

This is a genuinely different canonicalization from the layer form. An
implementation that assumes one rule for both will mint wrong bee signatures for
every module in the ecosystem. Pinned in the vectors deliberately.

Source of truth: `hypercomb-core/src/payload-canonical.ts`.

## 7. Storage layout

### Interchange form vs internal representation

This section defines the **portable interchange form** — the shape content takes
when it is exported, restored, backed up, or handed to another implementation.

**It does not mandate how an implementation stores content internally.** The
protocol defines the *logical* model (sig-addressed content, append-ordered
lineage bags, pools of meaning) plus this portable form. An implementation is
free to store records however it likes — packed files, a memory-mapped B-tree, a
database — provided it can **emit and ingest this form losslessly**.

That freedom is load-bearing, not academic. Content addressing produces very
large numbers of very small records (a marker is ~77 bytes; a hive can hold tens
of thousands), and one-file-per-record is a pathological shape for a filesystem —
particularly on Windows, where an on-access antivirus filter intercepts every
open. `hypercomb-client` therefore stores small records in a memory-mapped B-tree
and keeps only large blobs loose, while reading and writing the form below.

The web shell has both. Its flat OPFS layout IS this form; behind the
`hc:store:packed` flag it instead keeps small records in one packed file
(`<sign('store:packed')>/hive.pack`, owned by a worker over a
SyncAccessHandle) with blobs still loose and sig-named. The facade in
`hypercomb-shared/core/native-filesystem.ts` serves the form above live over
either backend, so callers cannot tell which is underneath — the same seam
the native client uses, with a second bridge behind it. Migration between the
two is per-record copy → verify → remove, with the flat layout as read
fallback until drained.

### The form

```
<root>/<sig>            content bytes — layers, resources (flat, sig-named)
<root>/<lineageSig>/    lineage sigbags (NNNNNNNN markers, max = head)
<root>/<sign(meaning)>/ pools of meaning
```

There are **no typed `__x__` folders**. They were eradicated and must never be
reintroduced, not even aspirationally. A new grouping is a *pool of meaning*.

Remaining legacy `__x__` directories are **self-cleaning drain sources**: opened
without `create`, read-fallback only, migrated and removed automatically.
**Writes never target a legacy directory.**

Lineage bags union-resolve across the root and every legacy source; the
**highest marker wins**.

## 8. Conformance requirements

A conforming implementation MUST:

1. Reproduce every signature in `vectors.json` byte-for-byte.
2. Apply lineage canonicalization, **including the symbol-only guard**.
3. Consult a self-extending pool registry before treating a sig-named directory
   as a lineage bag.
4. Emit canonical layer JSON with `name` first, slots sorted, empties dropped,
   and child order preserved.
5. Read both pointer and legacy-inline markers; write only pointer records.
6. Treat the maximum marker as the head.
7. Use insertion-order canonicalization for bee payloads and sorted-slot
   canonicalization for layers, and never confuse the two.
8. Never write to a legacy `__x__` directory or a legacy raw-key bag.
9. Never wipe user data — root sig files, lineage bags, or pools — outside the
   sanctioned per-record drain path.

A conforming implementation MUST NOT:

- Hardcode any pool address. Derive it; deriving registers it.
- Hardcode `EMPTY_LAYER_CONTENT_SIG`. It does not match the canonicalizer.
- Sort `children`.
- Normalize Unicode inside `sign()`.
- Assume `children` is positionally special in the canonical layer form.
