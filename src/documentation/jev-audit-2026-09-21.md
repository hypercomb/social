# Jev audit — measured against "everything happens from within the hive"

jwize, 2026-09-21: "The editor currently is VS Code but the real goal is to create only hive artifacts that hold everything … Then we can do away with VS Code and we can do away with GitHub."

This audit reads the Jev implementation as built (`documentation/jev-decisions.md`, `jev-creative-plan.md`) and the first pass of "the source lives in the hive" (`hive-read-fence.md` § Writing a module) and asks one question of every part: **does it live in the hive, or does it still need a repo, an editor, a terminal?**

## 1. What is sound

- **The rubric is one table.** Every question and every threshold is in `hypercomb-essentials/src/assistant/jev-decision.ts` (row questions, gates, reach gates, choice gates). Code composes; Jev only answers bounded questions; execution, budgets and authority never leave code.
- **The source boundary holds.** `jevUnseen` refuses any field the worker did not already see (verbatim, JSON-escaped, slash-free) and names it. The direct path, verify and file have their own boundaries.
- **Reach decides gates in code, never on the wire.** Additive skips grounded, editing needs all, destructive is never automatic.
- **Provenance is already hive artifacts.** Decision inputs, receipts, front-door and verify records are `putResource` atoms (`hypercomb-jev.ts`); outcomes and turn timings are records in the `jev:outcomes` pool (`jev-outcomes.ts`). Nothing about a decision needs the repo to be reconstructed.
- **Fallback is honest.** Jev off, no key, no grant, timeout or mid-turn failure all degrade to plain chat; only a boundary refusal asks the participant.
- **The module draft door is content-addressed all the way.** `module-drafts.ts` writes a new bee, a new layer, a draft root, and a pick — nothing overwritten, drop restores the trunk.

## 2. Findings — where the hive still leans on the outside

### 2.1 Code writes bypass Jev entirely (defect) — FIXED 2026-09-21

`jev-round.ts` `tableFor` wraps only `table` and `do` requests. A `hypercomb-write` block in Jev mode falls to the plain branch (`chat-window.component.ts:6779`) and runs through `runWrite` with no toward/beyond/grounded question, no doctrine sections, no choice gate. `JEV_WORK_INSTRUCTION` does not mention the write fence at all, so in Jev mode a worker has no row kind for "rewrite this module section". The single most consequential act in the hive — changing running code — is the one act Jev never judges.

**Fix:** a `write` row kind (reach `editing`, grounded required: the section must appear in evidence from a prior `read <sig> src/path`), body carried as a resource signature the row names (signature doctrine: never inline expandable content in a row). The doctrine questions then apply per section as they do for `do`.

### 2.2 The four module words do not exist — BUILT 2026-09-21 as `module list | drop <path> | commit [<path>] [<name>]`

The agreed shape was `module read · draft · run · commit` gated in Execution. Built: `read <sig>` / `read <sig> src/path` (read) and the model-only `hypercomb-write` fence (draft + run in one act). `listDrafts` and `dropDraft` have **no caller outside their spec** — a participant cannot list or drop a draft from the command line, and the only undo is knowing to reload after a drop that has no word. `commit` is not built.

### 2.3 "Deploy later" is still a terminal act (the GitHub half) — BUILT 2026-09-21 as `module commit`

Publishing a revision is `npm run publish:revision` → node builds → `stamp-install-channel.ts` asks the browser over the bridge to advance `install:essentials`. The browser already holds everything it needs (the draft root, the trunk's dependencies, the self activation door). Inverting it — the browser appends to `host:packages` and stamps the pointer itself as `module commit` — removes the last reason for a shell in the loop. Until then a draft is per-browser forever.

### 2.4 What a model reads is bundler output, not source

A section is esbuild-transpiled JS: types stripped, relative imports inlined, decorators lowered. A draft is JS; the `.ts` in the repo never learns of it, and `git` drifts on the first draft. This is acceptable under the stated direction only if the hive's JS becomes the source of truth outright — at which point `tsup`, `tsc`, the doctrine ratchets and vitest are orphaned, not merely bypassed. The owed atomicity step (one sig-named module per source file, `hive-read-fence.md` § Owed) is the precondition: today every draft rewrites a 2 MB bee to change one file.

### 2.5 Doctrine is baked at build time — BUILT 2026-09-21 (`anatomy-context-need.md` §2a)

`anatomy.generated.ts` is written by `hypercomb-essentials/scripts/build-anatomy.ts` from five `documentation/*.md` files at `prepare`. Jev judges rules that only change when someone runs npm and rebuilds essentials. For the hive to hold everything, the doctrine sections must be hive artifacts (resources named by a doctrine pool or a tile) that `anatomy.service.ts` reads at runtime; the source boundary still holds because the worker's system text is built from the same artifacts.

### 2.6 Tests and calibration live in node

Twelve vitest specs, the Playwright harness `scripts/verify-jev-table.cjs` (43 checks), and `scripts/jev-golden.cjs` (drives `jev-replay.ts` through the bridge intent `jev:replay`). The replay is already a pure in-hive function over receipts in the pool — it needs a word (`jev replay [rubric]`), not a script. The harness is the one piece that legitimately needs a browser driven from outside; the specs could become hive artifacts once source files are atoms.

### 2.7 Stale key in the participant question ordering (defect) — FIXED 2026-09-21

`jev-round.ts:348` reads `answers[<id>_fit]` to order the rows offered to the participant. Rubric v4 renamed the keys (`_needed`, `_toward`, …); `_fit` no longer exists, so every row scores 0 and "best first by Jev's fit" is dead — rows come out in the worker's order. Also `persistJevInput` stamps `rubric: 5` while `JEV_RUBRIC` is 4.

### 2.8 Jev is one hardcoded vendor endpoint

`JEV_ENDPOINT` is OpenRouter's `/api/alpha/decisions`; `JevDecisionService` reads the OpenRouter key directly rather than being a provider in the registry. An alpha endpoint is a single point of failure for every gated decision; the fallback (§1) contains the blast radius, but the provider plug-in architecture would let a self-hosted decision model take the seat.

## 3. Order, if the goal is "no VS Code, no GitHub"

1. **Writes at Jev's table** (2.1) — one row kind, one reach, body by signature. Small, closes the gate on the act that matters most.
2. **Words for drafts** (2.2) — `module list`, `module drop`, then `module commit` (2.3) as the in-browser `publish:revision`. After this the loop closes inside the hive.
3. **Doctrine as artifacts** (2.5) — read at runtime; a doctrine edit becomes a hive write Jev judges like any other.
4. **The atom is the file** (2.4) — builder change, then a draft is one file and the bee is a small entry naming its parts.
5. **Replay as a word** (2.6); fix 2.7 now.

What remains outside after all five: the Playwright harness and the shells' own `ng build`. Everything else — code, doctrine, decisions, outcomes, revisions — is a hive artifact.

## 4. Landed 2026-09-21 (steps 1 and 2)

- **Write row kind** (`jev-decision.ts` `write`, `WRITE_REACH`, `isChangeRow`): toward / beyond / grounded plus one question per doctrine section; always editing. `jev-round.ts` `tableFor` turns a bare write block into a one-row write table, `prepareTable` keeps the block in `writeOf` off Jev's wire and drops a write row a table lists without its block, `stepFor` yields a `write` step; the loop runs it through `runWrite` with Jev's review flag; the receipt names the code by resource signature (`body`). The worker instruction says to send the block alone.
- **Ordering fix**: the participant question orders by the live keys (`needed` / `toward` / `open`); receipts stamp `JEV_RUBRIC`.
- **Module words** (`assistant/module.queen.ts`; core `MODULE_DRAFTS_IOC_KEY` + `ModuleDraftsProvider`; runtime `module-drafts.ts` `commitDraft` + port): list, drop, commit (re-mint chain → new root → `host:packages` pool append → new trunk → `install:<name>` stamp via `setHiveRoot`).
- Specs: `jev-write.spec.ts`, `jev-round-write.spec.ts`, `module-commit.spec.ts`; the rest of the suite untouched and green.
- Not yet run against a live browser: a draft plus `module commit` on the web shell with jwize's key (the dev shell cannot draft). Core's contract changed, so the next `build:core` → `build:essentials` is needed before the web shell sees the word.

## 5. Landed 2026-09-21 (step 3: doctrine as artifacts)

- **Doctrine store** (`hypercomb-essentials/src/assistant/anatomy/doctrine.ts`): sections as resources, a record naming them, the `system:doctrine` bag (seeded in the pool registry). The anatomy service composes the anatomy from the head at runtime; the seed composes to the build's own bytes, so an unchanged hive sends exactly what it sent before.
- **Writing doctrine**: the write fence takes `doctrine <heading>`; Jev judges it as a write row but it is never automatic (`JEV_DOCTRINE_GATES`); the loop always holds it in Execution for the participant.
- **Participant words**: `doctrine`, `doctrine back`, `doctrine drop <n>`, `doctrine seed` (no machine grammar, so no model can say them).
- **Fixed on the way (step 1 defect)**: the write row carried a synthesized line and label, which Jev's source boundary refuses, so every Jev-mode write fell to the participant. The row now carries the header as written and a label cut from it; a spec proves the boundary passes.
- **Fixed on the way (step 2 hole)**: nothing in Execution gates on scope, so a model could have said `module commit` under an auto-run policy. The machine grammar now refuses `commit`.
- Specs: `anatomy/doctrine.spec.ts`, additions to `jev-write.spec.ts` and `jev-round-write.spec.ts`; 1428 tests across the touched suites pass; both shells type-check.
- Not proven live. The web shell needs `build:core` → `build:essentials` → `runtime:core` first, because core's contract changed in step 2.

## 6. Passes 2026-09-22 — real data, real tests, what broke

jwize: "make sure that we're getting value out of this Jev implementation; if not we need to think … real tests against the things we can do … manage Hypercomb without GitHub … create files and replicate automatically so people who have subscribed [receive them] when put out … if you turn something off it should be … not reachable — roots can be there but not served."

**Is Jev paying off? Not yet, on the evidence.** The hive's own record (`jev-decisions.md` §9): 14 outcomes, the direct path 0 of 11, the only table decision deferred, judged turns showing nothing for about 12 s. The sample is small and has no Jev-off baseline, so this is not a verdict on the design, but nothing in it shows Jev saving time or deciding anything. Where it demonstrably earns its place in the tests is as a GATE on changes (fit, overreach, grounding, one question per doctrine section, never automatic for doctrine or removals), not as a speed-up.

**Real tests.** `scripts/verify-hive-publish.cjs` (21/21) drives the whole "no GitHub" loop through the real web shell, the real content-host worker, real Nostr signatures and two separate browsers; only the model's and Jev's answers are scripted. `scripts/verify-jev-table.cjs` still passes 43/43. A run with real models needs jwize's OpenRouter key, which lives only in his hive; it was not run.

**Built this pass.**
- `module commit` commits what runs here: drafts in, turned-off paths out (unreachable, never deleted), and publishes before it stamps: every new file is uploaded and read back (`publishAtoms`), and only then does the signed pointer move. `@<host>` publishes to a host of your own.
- Followers take a pointer-named root from any host serving its root file (`rootHolder`), including the hosts the follow names.
- `scripts/local-content-host.mjs`: the public host's own worker code on this machine, for tests.
- The golden replay now reports outcomes by plan and turn timings.

**Defects the real run found, all fixed.**
1. `module commit` (step 2) stamped the pointer while the new files existed only in the publisher's browser: followers would be told of a package no host could serve.
2. The draft door wrote a new module as `<sig>`; boot and the loader look for `<sig>.js`, so the next reload failed the install check, wiped the install cache and cold-booted someone else's package. Fixed in `Store.writeBeeBytes`, which also served two other callers.
3. The module build keyed a NAMESPACE bundle on its own member files only; a bundle that inlines code from another folder (`commands` and `safety` inline the Jev service) never rebuilt, so a stale copy shipped and registered over the new one. Namespaces now record their real inputs like bees do, the quick "nothing changed" scan stats every recorded input, cache version 8.
4. The chat marked a write row `editing` and the Jev service refused any non-do row carrying a reach, so every Jev-mode write fell back to plain chat. Each unit spec passed; only the live run showed it.
5. The receipt rubric stamp: step 1 "fixed" it the wrong way (5 was right, the constant 4 was stale), which emptied the golden replay. The constant is 5 in both places, replay compares against it, and a parity spec holds them together.
