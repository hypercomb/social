# Module sandbox — every module change is reviewed in public before it goes live

**Status: the sandbox, its door, the host AI review, public assessments, the zone's trial listing, the what-changed panel, taking a trial into your own build, folding it into a build for everybody, Jev's public reading of every trial and Jev's pass over a zone's trials BUILT and proven on this machine (2026-09-23, `scripts/verify-hive-publish.cjs` 60/60); the worker is not deployed.** Builds on `hive-read-fence.md` ("Writing a module"), `jev-audit-2026-09-21.md` §6, `install-by-replication.md`.

jwize: "The idea of making a module — then we should go and debug it on a sub domain of one of our hosts, and that way we can review the code from our AI on that host, allowing us to make sure that it's in sandbox until we are happy with it. This should be the paradigm [for] new module changes, because you're basically publishing them to the public as well, so other people can view the code and make their own assessments."

## The paradigm

A module change is never published straight to the live channel. It goes to a **sandbox** first:

**Review before admission.** Visiting a trial and reading its source are
remote reads from that trial's door. The reader verifies each file against its
signature and sees missing files as missing. Neither action puts the trial's
code into the reader's hive. The trial may run on its own isolated origin so
its behavior can be observed. Its source diff, host AI reading, Jev reading,
and people's signed assessments are presented against the same exact package
root. These readings inform a person's choice; none silently takes or enables
code. `module take` is the first admission into that person's hive and holds
new code for a separate activation choice.

1. **Draft** — a model writes a module section; it runs here as a draft (built).
2. **Commit to a sandbox** — `module commit` uploads the new files to the host (built) and stamps a SANDBOX channel, `install:<change>`, in the publisher's signed index. The live channel (`install:essentials`) does not move.
3. **Debug at a subdomain** — `<change>.<zone>` on one of our hosts boots the hive with the package that channel names. Its own origin is its own storage, so nothing it does touches anyone's hive: the origin IS the sandbox.
4. **The host's AI reviews it** — the code the change added is read by the host's AI and scored by Jev, and the review is published beside the change as a signed resource. The pieces exist: the host's `/ai/ask` endpoint, and `safety/brood-audit.ts` (an agent reads held code, Jev scores accept or refuse, the verdict is only ever a score a person acts on).
5. **The public reviews it** — the subdomain is public and the modules are readable, unminified ESM (`code`, `read <sig> src/path.ts`). Anyone can read the change and leave a signed assessment on its root signature (built: `module assess`).
6. **Promote** — `module promote <change>` stamps `install:essentials` → the sandbox root. Same signature, same files: no rebuild, no re-upload, one pointer move (`feedback_packages_are_followed_pointers`). Followers see the update notice then, and not before.
7. **Withdraw** — the sandbox pointer is removed; the subdomain answers "nothing here". Its files stay on the host under their signatures: unreachable, never deleted.

## Decided (jwize, 2026-09-22): one live host

**Sandboxes go to `hypercomb.com`.** Its `*` wildcard is already live, and sites are already served at `<label>.hypercomb.com`. Nested labels are refused, so a sandbox and a site share one label space: every sandbox is named `try-<change>`, which no site uses.

## Decided (jwize, 2026-09-22): anyone's trial may be taken, held

A trial is taken into your own hive at one path whoever opened it — but what it brings does not run until you accept it in the brood with the two warnings. The alternatives were followed publishers' trials only, or doors only (no trial code enters a hive until a followed publisher promotes it).

## Build order (all four built, 2026-09-22)

1. Channel split: `module commit` stamps a sandbox, `module promote <change>` moves the live pointer, `module withdraw <change>` clears a sandbox. Local; proven by the existing harness.
2. The sandbox door: the worker route, the `package` field in `/site.json`, and the boot that takes its package from the door. Proven locally against `try-<change>.localhost:4291`.
3. The AI review: brood audit over the change's new modules on publish, with a signed report beside the change.
4. Public assessments: signed notes on the change's root signature, shown on the sandbox door.

## As built (2026-09-22)

- **Words** (`assistant/module.queen.ts`): `module commit [<change>] [@<host>]` commits what runs here, uploads the WHOLE package (the host skips what it holds — a HEAD per file), and stamps `install:try-<change>` only; `module promote <change> [<channel>]` moves the live channel (default `essentials`) to the sandbox's root with no upload; `module withdraw <change>` removes the sandbox key (`hive-pointer.ts` `clearHiveRoot`). All three are refused to a model. The toast names the door.
- **The door** (worker `serveSandbox`): `try-<label>.<zone>` answers `/content/<sign('host:packages')>/` with one member naming the approved publisher's `install:try-<label>` root, serves the package's files from the heap, describes itself at `/site.json` (`sandbox, package, pubkey, channel`), answers `/content/<sign('transfer:packs')>/<root>` with the TRANSFER PACK `module commit` sent beside it (`pack:try-<label>` in the publisher's signed index — every file of the package in one content-addressed file, so a cold visitor installs in a handful of requests; a hint, never load-bearing: no pack, and the install goes file by file), and proxies everything else to the participant shell (`SANDBOX_SHELL_ORIGIN`). No stamp → "nothing here".
- **The boot** (web `ensure-install.ts` `sandboxDoor`): on a `try-` origin the cold boot takes its package from the door alone — never another host, so a sandbox can never silently run the live package.
- **Loopback**: any `*.localhost` is loopback in the runtime, the upload and the signed index, so a door is proven at `try-<change>.localhost:<port>` and writes go to `content.localhost:<port>`, the zone's content face, as in production.
- **Back-to-back writes**: the signed index stamps whole seconds and the host refuses a same-age index as a rollback; every write now names the index it replaces and is stamped at least one second after it (`putHiveManifest` `replaces`).
- **The change and the host AI's review** (`assistant/module-review.ts`, a dependency the `module` queen drives): every commit writes THE CHANGE down — each drafted source file before and after, each its own resource, plus the paths left out — publishes it and stamps `change:try-<change>`; then asks the host the sandbox lives on (`/ai/ask`, NIP-98 signed, `HostAiService.askWhole`) with those before/after files as context, so the host reads the code from its own heap; the findings and a verdict (accept · refuse · unclear, the last `VERDICT:` line) are published as `review:try-<change>`. The door's `/site.json` names `change` and `review`. `module review <change>` reads it again. A verdict is a reading, never a gate: promotion stays the participant's word. The host AI sees at most 8 files of 16 KB, which is why the change is cut to sections and never handed over as whole bundles.
- **Public assessments** (`module assess <change> [accept|refuse|unclear <note…>] [@<host>]`, `assistant/module-review.ts` `assessSandbox`): ANYONE may assess a sandbox, under their OWN key. An assessment is a record in the heap — `{ kind: 'module-assessment', sandbox, root, change, verdict, note, at }`, the note its own resource — that the assessor names in their own signed index as `assess:<package root>`. The signature on their index is the signature on the assessment; it is never written into the publisher's index, and it is not a pheromone (a verdict, not an interest signal). The host keeps a derived list of who assessed which root (`assessors:<root>`, written on the index PUT) and never trusts it: the door's `/site.json` re-reads and re-verifies every listed assessor's index and lists only assessments whose record names that root (at most 50), plus `reviewVerdict`, the host AI's verdict. Without a verdict, `module assess <change>` says the tally from anywhere; the door itself says it once on boot (`assistant/sandbox-door.drone.ts`, which also emits `module:door` with the whole descriptor). Like the review, an assessment is a reading, never a gate.
- **The trials on a zone** (worker `serveTrials`, `GET /trials.json` on the zone's apex or any door on it; word `module trials [@<host>]`): every open trial, listed from what its door serves — each `install:try-<change>` key in the verified index of a publisher the zone approves goes through `resolveSite` and `sandboxRoot`, the two reads the door itself makes, so the listing never names a door that answers "nothing here", and where two publishers name one trial it lists the one the door serves. Each entry: name, door, package, publisher, when it was committed (the change record's `at`, stamped from 2026-09-22), the source files the change touched (`sections`) and the paths it turned off (`off`), and the host AI's verdict. Newest first, at most 100; a zone whose `*` route is not up lists nothing. People's assessments stay at each door's `/site.json`, where every one is re-verified. The word says the newest six one by one (whose, when, what, the AI's verdict, the door) and emits `module:trials` with the whole listing. It reads; it publishes nothing.
- **One difference at a time** (`module changes <change> [@<host>]`; the panel `assistant/sandbox-change.view.ts`, wired by the sandbox feature's bee `sandbox-door.drone.ts`; the reading `module-review.ts` `readTrial`; the diff `assistant/line-diff.ts`): opens over any hive — the publisher's, a tester's at the door (no host needed there), anyone's. It walks the trial's change file by file, before and after (Myers line diff, three lines of context, longer unchanged stretches folded to a count), says what the trial turned off, shows the host AI's verdict and findings and every signed assessment with its note, links the door, and steps to the previous or next trial the zone lists. Everything is read by signature from the trial's door, and only bytes that hash to the signature asked for are believed; a side that cannot be read is named as missing, never drawn as an emptied file; notes and findings are drawn as text, never markup. It reads; it publishes nothing.
- **Your own build** (`module take <change> [<path>] [@<host>]`, or "take" on a file in the what-changed panel; `module-review.ts` `takeTrial`): the trial's layer at each path its change touched (or the one named) becomes a pick in this hive, made BY HAND. The runtime's activation gate has a door for exactly this (`activation-authority.ts` HAND; `install-by-replication.md`): a hand pick from a root nothing here vouches for is let in as a STRANGER's arrival, never over a forged index. `pickRevision` then holds in the brood every bee AND dependency bundle it brings that the trunk does not already run (a byte-identical copy of the trunk's own code is not held — holding its signature would hold the trunk's copy too), never records the root as trusted, and marks the pick `byHand`. The selection composes only what may run (`composeDependencies` asks `mayRunBee`): a held bundle waits and the trunk's bundle for its namespace keeps running; held bees are left out of the sideways and core-surface checks until accepted. Accepting by hand (`brood accept <sig>`, or the brood panel) says `brood:ruled` (safety/brood-accept.ts), and the sandbox feature's bee composes the selection again so the accepted code runs after a reload. If a publisher you follow later promotes the same bytes, the held record takes that source (core `holdArrivals`: a record's kind only ever moves up, and your ruling is never touched), so your rules for followed code decide it. `module list` names what was taken by hand; `module drop <path>` gives the path back to the trunk. The word is the participant's alone: a model never brings somebody else's code into a hive.
- **A build for everybody** (`module commit`, runtime `commitSelection`): a commit is WHAT RUNS HERE — the trunk with every pick that applies laid in at its path, drafts and everything else alike: a trial taken by hand, a revision picked in Packages. Each folded pick brings the namespace bundles its root lists under its path; the render hint follows the new tree; folded picks stop being picks. A pick whose code still waits in the brood is NOT folded — a commit publishes under this hive's key, and code nobody here accepted never rides out under it — so it stays a pick and the commit says so (`held`). The change record names what was folded in and from which root (`taken`), the host AI's question says it, and the what-changed panel shows it. A fold that changes nothing is "nothing to commit". The same composition is the same signature wherever it is made: a hive that folds exactly one trial into the same trunk rebuilds that trial's root byte for byte, so builds converge across the community instead of multiplying.
- **The draft audit** (jwize, 2026-09-23: "a code safety audit so we can author our own new code in real time"). A section a model writes back runs in the author's own hive, beside their keys — so before it can run, two readers look at it, and either may HOLD it; neither can ever let it run.
  - *The scan* (core `code-reach.ts`, instant and deterministic): what the new section reaches that the section it replaced did not — the network (or an address the old code never named), stored data, secrets and keys, text run as code, a way out of the page, disguise. Comments are read too. The draft door (runtime `draftModule`) records every draft in the brood as your own code BEFORE its pick is made; one that newly reaches anything is flagged there (core `flagInBrood`: a flag only holds, and only a ruling — the hand — decides past it). A hold that cannot be recorded means nothing is applied. The chat tells the participant and the model which reach held it, and tells the model not to work around it.
  - *The reading* (essentials `safety/brood-audit.ts` `auditDraft`, on `module:drafted`): the participant's chosen model reads the change — the section before and after, fenced as data — and JEV scores that reading; either recommending refusal holds the draft. A reading that saw only part of the code never recommends letting it run. The same code is read once. The toast names who actually read it.
  - *The hand*: `brood` lists every draft (yours, runs — or held, and why); accepting one with the two warnings composes the selection again, so it runs after a reload. `module commit` never folds a held draft — before this, drafts skipped the brood check entirely.
  - *Proof*: specs (scan, flags, draft door, commit, reading); `verify-hive-publish.cjs` still 60/60; and a live run on the web shell — a clean draft runs, a draft that newly reaches the network is held, stays inert across a reload, is left out of a commit, and runs once accepted (12/12).
- **Risk levels and `brood scan`** (jwize, 2026-09-23: "do llm scans and JEV scans on the brood and then give a risk level or code review"). Every brood record wears a level code composes from what the brood already knows (essentials `safety/brood-risk.ts` `riskOf` — the readers list, JEV judges, code composes): **high** when the code reaches secrets and keys, runs text as code or is disguised, or anyone — a reader, JEV, a community you follow — recommends refusing it; **medium** for the network, stored data or a way out of the page, or a reading that could not tell; **low** when read, accepted and reaching nothing of the kind; **unread** otherwise. `brood scan` (asked for, never on a timer) records what every held automaton reaches (`scanHeld`; your own drafts were scanned at the draft door against the code they replaced) and has the participant's model and JEV read what nobody has read — a few per pass, each spends the model — then says the levels. `brood list` and the brood panel show each record's level and reasons; the panel's **Review** opens the reader's full findings (the report resource). A level is advice: only the hand lets held code run. Live: 6/6 on the web shell.
- **Jev reads every trial, in public** (`assistant/jev-decision.ts` "Jev reads a trial", `JevDecisionService.reading`, `module-review.ts` `jevReadTrial`): on every commit, and again on `module review`, Jev judges the change's diff — every line added and removed, a little context around each, cut to the read budget — against every doctrine section with the same rule question a write faces. A write shows Jev only its header and its reason; the reading shows it the changed lines themselves. The record (`jev:try-<change>`, `{ kind: 'jev-reading', verdict, files: [{ section, rules: [{ rule, breaks }], worst }] }`) names each file's chance of breaking each rule and the change's standing — follows within the pass gate, breaks past reject, unsure between. The door's `/site.json` and the zone's `/trials.json` carry `jev` and `jevVerdict`; the what-changed panel shows the standing and each file's rule closest to breaking. Gated like every Jev act — Jev switched on, OpenRouter allowed to read the hive — and the source boundary is the published change itself: only what is public is judged. A reading is a reading, never a gate: promotion stays the participant's word. jwize, 2026-09-23: "the primitive should be enforced so everything is replayable and reviewable".
- **Jev weighs the zone** (`module focus [@<host>]`; `assistant/jev-decision.ts` "Jev weighs a zone", `JevDecisionService.pass`, `module-review.ts` `jevPassZone`): the open trials, weighed together. Code gathers what is known about each trial from public records alone — the zone's listing, each door's site and the signed change, reading and assessment records behind it — and writes it in plain words: what it changes and turns off, how the host's AI and Jev read it (with the rule it came closest to breaking), how many accepted and refused and what their notes say, which trials took its package (adoption, from the `taken` field of the signed change records, now carried by `/trials.json`), and which other trial changes one of the same files. Jev answers one batch over that table — does each trial conform, did anyone refuse it, and which to focus on first (JEV RUNS THE SHOW: the table is code's, the snap judgments are Jev's, the composition is code's) — and code composes each trial's standing: a refusal past `beyond` is to DISCUSS, conformance past `toward` is to TAKE, anything else WAITS; the focus is Jev's choice when confident past the floor. Two trials changing one file are named as a clash: one layer per path, so only one can be folded, or a merge drafted. The pass (`{ kind: 'jev-pass', zone, trials: [{ name, standing, conforms, refused, clashes, takenBy }], focus }`) is published under the participant's key as `pass:<zone>` — replayable and reviewable like everything else. It proposes; it takes nothing and folds nothing: `module take` and `module commit` stay the participant's words. jwize, 2026-09-23: "JEV can also make decisions across this network for us."
- **The trail wears the Life Primitive** (`module-review.ts` `putHop` / `openHop` / `openChange`; `life-primitive.md` "The sandbox trail wears it"): every hop a reader opens in the published records — a section's text before and after, the host AI's findings, an assessor's note — is a meta envelope with one `resource` payload and its relation named, so the trail is traversed by the same rule as any tree; what a reader matches (the package root, the change a reading is of) stays a signature, as an index key does. The host serves the text and the envelope; the host's AI and Jev are shown the text; records from before 2026-09-23 with raw signatures still read. TRAP: the runtime store's `getResource` already follows a resource incidence, so a reader that must hand on the terminal signature (the review's context) reads raw first (`getResourceLocal`) — the first run sent the host the envelopes' signatures and the host's AI was shown two envelopes. jwize, 2026-09-23: "every part of the experience shares the same properties".
- **Proof**: `node scripts/local-content-host.mjs 4291 http://localhost:4260 --ai-stub` (the real worker code over memory storage; `POST /__bind` stands in for the operator's binding; `--ai-stub` answers only the upstream Anthropic call, and says how many files it was shown and whether the changed code was among them), the web shell on 4260, then `node scripts/verify-hive-publish.cjs` → 60/60 (the tester at the door is told what it runs, signs a refusal with a note, the door lists it under the tester's key, and the publisher reads the tally from its own hive; the zone lists the trial with what it changes, the tester finds it with `module trials` from inside the door, the listing says what a later trial turned off, and a withdrawn trial leaves the list; the publisher opens the change in the panel — the model's added line, the host AI's verdict and the tester's signed note — and the tester opens the same change at the door with no host named; the follower takes the trial by hand — one new bee held, still not running after a reload — accepts it with `brood accept` and both warnings, and runs it after the next reload; then the follower commits its own build — the trial it took plus a unit of its own turned off — and the trial's layer is part of its package, no longer a pick, and named with its root in the follower's published change; then the publisher says `module focus` and Jev's pass is public: the refused trial is to discuss, the follower's is to take and is the focus, and the pass names that the follower's trial took the publisher's package). ## Door safety (built 2026-09-23)

jwize: "your peer hosts become your sandbox and you can scan the signed files by signature and audit them using your favorite AI" — so a door must be safe for whoever tries it. At `try-<change>.<zone>` the publisher's package runs with full page power; the origin boundary holds (a fresh key, no keys, none of the visitor's hive), and these close what leaked around it:

- **The local bridge trusts no web page.** Both brokers (`scripts/bridge/run-bridge.cjs` via `bridge-origin.cjs`, and the CLI's `hypercomb-cli/src/bridge/server.ts`) refuse a WebSocket handshake whose `Origin` is present and not exactly localhost / 127.0.0.1 / [::1] — a door, or any site, can no longer drive the broker. `/healthz` answers CORS only to such a page.
- **The door page wears its own policy** (worker `serveSandboxShell`): `connect-src 'self' https: wss: blob: data:` (plus exactly the zone's two http faces on a loopback zone — never a bare `http:`/`ws:`, so the visitor's machine is out of reach), `worker-src 'self' blob:`, `frame-ancestors 'none'`, no forms, no devices, no referrer, COOP, no cookie. Scripts are left alone (the import map and blob: bees).
- **A door writes nothing.** The content worker and `relay.js` refuse every write whose `Origin` is a door (a `try-` first label) or opaque (`null`: a sandboxed frame or data: worker a door opens) — before any route. A door host runs no worker from the heap (a worker takes its policy from its own script). The limit: a signature coaxed out of an extension can be replayed from elsewhere, so the extension's own prompt stays the last guard.
- **The shell knows it is at a door** (core `sandbox-door.ts`, the one predicate; a ratchet refuses a local `try-` regex): no LLM key is stored or read there, `window.nostr` is pinned away before anything loads, the web shell draws a door bar (plain DOM, before bootstrap — at a door every module is the publisher's), and the words that write refuse there and point home.
- **Proof**: `verify-hive-publish.cjs` 67/67 — the door's CSP, a blocked dial to `ws://localhost:2401`, a refused write, no key kept, no extension signer, the door bar, the refusing word, and the assessment signed from the reader's own hive.

**Still open (need jwize):** a **dedicated door domain on the Public Suffix List, served by a door-only worker** — until then a door is same-site with every site on its zone, and on the shared worker it takes `/core/*` and its service worker from the deployed visitor assets, so doors break when core moves unless the visitor assets are deployed with hypercomb.io. **`AI_WRITERS`** is empty, so any signer can spend the host AI (lock it to bound publishers if no participant-hosted AI relies on it). A **framed door** (the shell's bar in a parent document the package cannot touch) comes with the dedicated domain.
