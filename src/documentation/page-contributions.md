# Page contributions — edit a live site's words, drop them in a pool, toggle and compare

**Status: plan, 2026-11-12. Step 0 is built (uncommitted at time of writing). Steps 1 to 6 are not built. Four decisions at the end wait on jwize.**

jwize, 2026-11-12:

- "For all websites that we deploy if we have the publish key can we make it so we can edit the text inline (no html)."
- "allow clicking the text and popup the input in a nice formatted input something like the style on the notes input."
- Asked whether it should also work on the live subdomain: "Yes … this is important because we want to develop across domains and toggle between them and compare."
- "Everyone can drop their contributions in pools."

So an edit to a live page does not overwrite the page. It is a **contribution**: a new version of that one page, signed by whoever made it and dropped in a pool anyone can read. The site keeps running what its publisher published. Any reader can **toggle** between the published page and the contributions, and **compare** any two. The **key holder's pick** decides what everyone is shown.

This adds no new mechanism where one exists. A contribution is a published-pool member, a claim in its maker's own signed index, the shape community translations already use (`community-translations.md`). Toggling is a local pick, the shape `revisionsOf` / `pick` already give code (`hypercomb-runtime/src/acquire.ts`). Comparing is the existing what-changed panel. The live page will be the debugger page (`debugger-chat.md`): one subdomain, and having the key changes what you can do there.

## Step 0 — editing in your own hive (built 2026-11-12)

A site page open in your own hive shows a pencil above the exit button. It appears only for a page that is yours (not adopted from another publisher), only where this place holds a key, and never on the read-only published shell. With the pencil on, any text answers a click with a notes-style input. Enter saves a new version of the page with only that text changed, and the tile points at it, so the old words are one undo away. Text the page's own script draws is refused, because it is not in the page's bytes.

- `hypercomb-essentials/src/presentation/tiles/site-text-edit.ts`: the pencil, the hover mark, the input, and `replaceTextInPage`. A text is addressed by its place in the AUTHORED page (element index in document order, text-node index), never by the live DOM.
- `hypercomb-essentials/src/files/page-commit.ts`: one way a tile is pointed at a new page, shared with a model's write block (`tile-files.drone.ts`).
- `site-view.drone.ts` offers the pencil and saves the edits.

Steps 1 to 6 reuse all of it. The input stays the same and only the save changes: on a page that is not yours, or on the live site, Enter drops a contribution instead of committing to a tile.

## What the trace found (2026-11-12)

- **A live page cannot republish a site.** The visitor engine on `<name>.<zone>` runs on an in-memory filesystem with every write refused except a pool member PUT (`hypercomb-web/src/setup/readonly-network.ts`). A real publish seals the subtree (`history.service.ts` `sealSubtree`), uploads every atom the host lacks to the zone root (`host-sync.service.ts`), then signs the index. A head signed without its atoms on the host is a dead link.
- **One page and one signed claim is cheap.** `hypercomb-shim/src/bootstrap/device-owner.ts` already does it from a phone for the showcase. It uploads one record to `https://<zone>/<sig>` (HEAD first), reads the anchor's index fresh, sets one key in `roots`, and signs kind 30564 with `['anchor', …]` and `['prev', …]`, so two places writing at once cannot drop each other's change. A contribution is exactly that shape: one page resource (everything else it names is the base page's, already on the host) and one key in the contributor's own index.
- **A new index alone moves a door.** The worker appends the door marker during the index PUT (`worker.js` `advancePublishedLocations`). Nothing extra is written for a pick to show.
- **Nothing pulls a newer head of your own lineage back home.** Device sync pulls from a paired device only, on a button. Step 5 avoids needing one.
- **The key on a site's origin is readable by that page's scripts.** A device key lives in `localStorage['hc:nostr:secret-key']` on its origin (`device-key.ts`), and site pages run their scripts on that same origin. See decision 3.

## The shape

| Piece | What it is |
|---|---|
| A contribution | a page's new bytes, a resource. Made with the step 0 input: words only, never markup. |
| Its claim | the contributor's own signed index names it under `page:<base>`, where `<base>` is the signature of the page they edited (decision 1). Signed by the contributor; the host never vouches for it. |
| The pool | the host lists every contributor's key at `<origin>/<sign('page:<base>')>/`, one per line, the same membership listing as a name's picture pool and an attestation pool. The listing is never believed on its own: the reader reads each contributor's own signed index, checks the page it names hashes to that name, and decides words-only against the base. No registry: a reader derives the address from the page it is looking at and asks. Because the key is a content signature, the same page published on two domains finds its contributions on both. |
| Text-only | a contribution whose element structure, attributes, scripts and styles are byte-identical to its base, so only text nodes differ. Viewing one runs nothing its base did not already run, so it needs no review. Anything else is foreign content and goes through the activation gate (`page-run-gate.ts`) like any adopted page. |
| Toggle | a reader's own local choice of which version of this page to show: the published one or any contribution. It is never published and never changes what others see. It is the site's version of the install `pick`. |
| Compare | any two versions, opened in the what-changed panel, diffing their visible text (`inertPageText`). |
| The pick | the key holder's choice, signed in their own index as `pick:<base> = <contribution sig>` (decision 4). The site view renders a page through its publisher's picks, so the pick is what everyone is shown. A pick is truth (signed, in the index), not a cache. |

Chains: a contribution to a contribution has the first contribution as its `<base>`. The revisions of a page are its own pool plus the pools of each base it came from, walked back through the claims.

## Steps

Each step ends in something a person can see, and a step starts only after the one before it has been seen working.

**Step 1 — the text-only check (done 2026-11-12).** A pure function: do two pages differ only in text nodes? Plus its spec. *Done when:* the spec proves a changed word passes, and a changed attribute, script, style or element fails. *State:* `presentation/tiles/page-text-only.ts` `differsOnlyInText`, spec `page-text-only.spec.ts`. Code text (`<script>`, `<style>`), comments, the doctype, every attribute and a `<template>`'s content must match exactly; words that turn into markup fail; what the step 0 editor writes passes.

**Step 2 — drop a contribution from a hive.** On a page that is not yours (adopted, or a followed host's site), the pencil now shows too. Enter makes the new page, uploads it to the publisher's zone root, and adds `page:<base>` to your own signed index there. This is the device-owner write shape with your hive's signer. *Done when:* an edit made in one hive is a verified member of `sign('page:<base>')` on the publisher's host. *State (done 2026-11-12, except the listing, which is step 3):* `sharing/page-contributions.ts` `dropContribution` (refuses anything but changed words, before a byte leaves), on `sharing/host-offer.ts`, the one offer shape now shared with `language offer`. The site view picks the mode per page: yours saves into the tile, anything else offers to its publisher's zone (the broker's attribution, `pagePublisherDomain`). With no host known, the input opens read-only and says so. Proven against `scripts/local-content-host.mjs` (the real worker over in-memory storage): the host held the contributor's own signed index (kind 30564) naming `page:<base>` → the edited page, whose bytes hashed to their signature, and the page in the hive stayed as published. Not proven against a deployed host.

**Step 3 — the pool is listed.** The host serves `sign('page:<base>')` for every base that has claims, as it serves `sign('i18n:<locale>')`. First check whether the worker's published-pool listing already covers a new `roots` prefix with no change. *Done when:* any client derives the address from a page signature and reads its contributors. *State (done 2026-11-12):* it did not; the worker now keeps contribution pools the way it keeps picture pools (`notePageContributors` and `isPagePool` in `hypercomb-relay/blossom-worker/worker.js`: an index naming `page:<base>` makes the contributor's key a member of `sign('page:<base>')`, and that address a member of `sign('page:pools')`, so the listing route knows it). The reader is `readContributions` in `sharing/page-contributions.ts`: listing → each contributor's verified index → bytes hashed against their name → words-only decided against the base, newest first. Proven against the local host with a contribution made through the UI in a second hive. **Deploying it is the operator's step**: until the worker ships, a deployed host holds contributions but lists nobody.

**Step 4 — the revisions strip, toggle and compare.** A small strip on the site lists this page's versions, newest first: the published page, then each contribution from the page's own host and from every host you follow. A row shows who made it, where it came from, and when, and whether it is text-only. Clicking a row toggles to it locally, and checking two rows compares them. It works the same in your hive and on the live site; this is "develop across domains, toggle between them and compare". *Done when:* two contributions from two hives and the published page are listed, any two compare, and a toggle changes the page on screen. *State (done 2026-11-12):* `presentation/tiles/site-versions.ts` (the `layers` button above the pencil, its count, the panel; compare by `diffLines` over `inertPageText`), wired in `site-view.drone.ts` (`#offerVersions`, `#versionHosts`, a reader's choice in `#shownVersions`, never written anywhere). Proven with two hives (4253, 4254) each offering through the UI to the local host: hive A listed the published page and both contributions, a click put hive B's words on hive A's page with the tile unchanged, and ticking A and B showed `− Hello there, from hive A` / `+ Welcome, from hive B`. Not yet: an offer made while viewing a contribution lands in that contribution's own pool, and the strip does not walk those chains back.

**Step 5 — the key holder picks.** On a row, a key holder can **Use this for everyone**. It signs `pick:<base>` into their index with the device-owner shape. The site view resolves a page through its publisher's picks before mounting, both on the live site and in the publisher's own hive, so home shows what the live site shows with no pull-back. The next full publish from home folds the picks into real commits (the step 0 page commit) and drops them from the index. *Done when:* a pick made in one place changes the live page for a stranger and shows in the publisher's hive. *State (done 2026-11-12, without the fold):* `readPick` / `signPick` / `pickDeps` in `sharing/page-contributions.ts`. The pick is `pick:<base>` → the chosen page in the publisher's ONE index (every place that publishes for them writes it); the reader takes the newest copy any of the page's hosts holds, so a cleared pick is honoured, and believes it only when its bytes hash to their name. The site view (`#resolvePick`, after the page is up — view first) renders a page through its publisher's words-only pick; a reader's own toggle, the published page included, wins over it. Whose pick: a published creation's publisher (`preview:mode` names them and their hosts); in a hive, its own pages, read from its own index on the hosts the page publishes to (`#pickHosts`). Only the creation's publisher gets **Use for everyone** — on a hive viewing someone else's published creation the buttons are absent. Proven with the local host and two hives: the owner (4253) picked its version; a stranger (4254, another key, nothing toggled, given the same `preview:mode` the visit engine emits) saw it with the row marked "everyone sees this" and no buttons; the owner took it back with **Use for everyone** on Published and the stranger saw the published page again after a reload. The stranger was a hive, not the real published shell; the published shell reads the same way from its own door (`location.host`). Not built: the fold into commits on the next publish (today the pick stays in the index until the page changes, and the owner's edits made while the pick is shown are made on the picked words, which folds it then); "higher wins" waits for branch-scoped keys. After the live run, the reader's host reads were moved onto `readPoolListing` and `fetchWithDeadline` (doctrine ratchets); that change is covered by specs, not re-run live.

**Step 6 — edit on the live site itself.** The step 0 input on `<name>.<zone>`: Enter drops a contribution (step 2), and a key holder also gets **Use this for everyone** (step 5). This needs a key on that origin and a binding that survives a reload; the visitor engine's store is in memory, so the binding must be kept in what persists there (decision 3). It belongs on the debugger page when the website view and the editor's pencil move off Angular (`debugger-chat.md`, port step 3), not as new work in the Angular visitor engine. *Done when:* a key holder on a phone edits a heading on the live site, picks it, and a stranger sees it.

## Keys at any level (jwize 2026-11-12, decided)

jwize: "The key should be able to be shared at any level perhaps. and if at the root it is the default." Then: "so they override if they are futher up." Asked whether that means the higher key wins over a branch key, he answered "Yes, higher wins" (not "nearest wins"). So handing out a branch key never costs the root's holder control of their own site.

- **A key can be given for a branch, not only a whole site.** Someone holding the key for `/site/blog` may pick for every page under the blog and nowhere else.
- **A key given at the root covers everything below it.** That is the default, and it is what every key is today.
- **When two keys disagree, the one further up wins.** If the blog's key holder picks one version of a blog page and the root's key holder picks another, everyone sees the root's pick. At the same level, the newest pick wins.

How it fits what exists: the key list (`hypercomb-core/src/core/key-list.ts`, one signed chain per anchor at `sign('keys:lists')/<anchor>`) gains one optional field per key and per invite, its scope: a lineage, the same keys the signed index already uses for `roots`. A key with no scope is a root key, so every list already on a host keeps its meaning. `keys allow <place> [<branch>]` writes an invite for a branch. A reader honours a `pick:<base>` only when the signer's key is on the publisher's list with a scope covering the page's place, and settles disagreements by the rule above. A branch scope is a route, which the molecule doctrine says is never an address. Here it only bounds a permission and never finds anything, the same use the index already makes of lineage keys. This is also the same shape as a website's hide record: the root's record is the whole site's switch, and a lower one covers its branch.

## Decisions for jwize

1. **What a contribution's pool is keyed by.** Recommended: `page:<signature of the page edited>`. It is content-addressed, needs no name or path, and works across domains as is ("only signatures are queried"). The alternative, the tile's route under the site (`page:/business/people`), reads better but is a route, not an address, and collides wherever two sites share a page name.
2. **Who may drop a contribution.** A contribution has to be signed to be attributed. Recommended: anyone who already holds a key, meaning a hive or a device that accepted an invite. A stranger on the live page holds none, and `device-key.ts` says only the Allow tap makes one. The alternative is to offer a stranger "make a key to contribute" on the live page.
3. **Where the key lives on a site's origin.** A key in that origin's localStorage can be read by the page's own scripts. That is the owner's own code for their own site, but a site that seats other people's parts runs their scripts there too. Recommended: on the live site a key holder signs through a same-site window on the zone apex that holds the key and asks for each signature in its own UI. The page's scripts then never see the key. The alternative accepts the risk and keeps the key on each site's origin, via `keys allow <name>.<zone>`.
4. **How the key holder's choice reaches everyone.** Recommended: a signed `pick:<base>` read at render time (step 5). It needs no seal and no upload from the live page, and home sees it at once. The alternative is a full republish from the live page, which would need the seal-and-upload machinery the visitor engine lacks today.
